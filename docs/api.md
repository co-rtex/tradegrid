# Sprint 2 API and Exchange Contract

This document is the shared contract for Sprint 2 ([issue #30](https://github.com/co-rtex/tradegrid/issues/30)). Backend, frontend, testing, and database contributors build against it independently. Change it through a pull request before changing code that depends on it.

Sprint 2 scope: one local, single-process, in-memory exchange with two seeded demo accounts, REST over standard Go `net/http`, and correct reservations and settlement. Authentication, cancellation and amendment, WebSockets, runtime persistence, and P&L are later milestones.

Related documents:

- [Order Domain Model](order-model.md) defines `orders.Order`, its enumerations, and lifecycle.
- [Matching Engine Behavior](matching-engine.md) defines price-time priority.
- [Portfolio Accounting Contract](portfolio.md) (Sprint 3) defines cost basis, P&L, reference prices, and `GET /api/v1/portfolio`. It adds to this contract and changes nothing in it.
- Order input validation ([issue #3](https://github.com/co-rtex/tradegrid/issues/3), PR #29) defines the logical input rules. That draft says the backend has no serialized order model; `orders.Order` now has JSON field names (from #6), and this document fixes the wire format, symbol list, case rule, numeric bounds, and short-selling policy that #29 lists as future decisions.

## Conventions

| Topic | Rule |
| --- | --- |
| Base path | `/api/v1` |
| Content type | Requests with a body must send `Content-Type: application/json`. Responses are `application/json; charset=utf-8`. |
| Field names | `camelCase`. |
| Money | Integer US cents. `19050` means $190.50. Never a JSON float or string. |
| Quantities | Integer whole shares. |
| Enums and symbols | Exact uppercase strings: `BUY`, `SELL`, `LIMIT`, `NEW`, `AAPL`. `buy` or `aapl` is invalid; the server does not normalize case. |
| Timestamps | RFC 3339 in UTC with a `Z` suffix, for example `2026-10-20T15:00:01Z`. Fractional seconds may appear. |
| IDs | Opaque strings generated by the server, for example `ord-1`, `exe-1`. Clients must not parse them or depend on their format. |
| Sequences | Positive integers generated by the server. Orders carry an acceptance `sequence`; executions carry an execution `sequence`. Each counter starts at 1 and strictly increases. Sequences, not timestamps, define order: equal timestamps are expected. |
| Collections | Always an array inside a named object, for example `{"orders": []}`. An empty result is `[]`, never `null` or a missing field. |

## Numeric Bounds

Bounds keep every value an exact integer in both Go `int64` and JavaScript `Number` (largest safe integer `2^53 - 1 = 9007199254740991`).

| Value | Bound |
| --- | --- |
| `price` | `1` to `100000000` cents ($1,000,000.00) |
| `quantity` | `1` to `1000000` shares |
| `price × quantity` | at most `1e14`, which the two bounds above guarantee |
| Any account total, reservation, or order-book level quantity | at most `9007199254740991`. An operation that would exceed it is rejected with `LIMIT_EXCEEDED` and changes nothing. |
| Request body | at most 4096 bytes |
| `limit` on list reads | default `50`, maximum `200` |
| `depth` on order-book reads | default `20`, maximum `100` |

## Demo Accounts and Symbols

The exchange starts with exactly these accounts and no orders. `userId` selects a demo account; it is not authentication.

| `userId` | `displayName` | Cash | AAPL | MSFT |
| --- | --- | --- | --- | --- |
| `alice` | `Alice (demo)` | `10000000` ($100,000.00) | 100 | 100 |
| `bob` | `Bob (demo)` | `10000000` ($100,000.00) | 100 | 100 |

Tradable symbols are `AAPL` (Apple Inc.) and `MSFT` (Microsoft Corporation).

Restarting the server resets everything to this state. There is no reset, deposit, or account-creation endpoint. PostgreSQL seeds ([#39](https://github.com/co-rtex/tradegrid/issues/39)) use the same accounts and balances; the runtime exchange does not write to the database in Sprint 2.

## Reservations and Settlement

Every account has, for cash and for each symbol, a `total`, a `reserved` part, and `available = total - reserved`.

**Accepting an order (preflight).** Only one order type is supported: `LIMIT`.

- `BUY`: requires `available cash >= price × quantity`, then reserves `price × quantity` cash.
- `SELL`: requires `available shares >= quantity`, then reserves `quantity` shares. There is no borrowing or short selling.

A rejected order creates no order, no reservation, and no execution, and it is not stored.

**Settling one execution** of `q` shares at execution price `p` (always the resting order's price), where the buy order's limit is `L`:

| Account | Cash total | Cash reserved | Shares total | Shares reserved |
| --- | --- | --- | --- | --- |
| Buyer | `- p × q` | `- L × q` | `+ q` | — |
| Seller | `+ p × q` | — | `- q` | `- q` |

When `p < L` (price improvement), the buyer pays less than was reserved and `(L - p) × q` returns to available cash. A resting order keeps the reservation for its remaining quantity.

**Same-account trades.** If one account's orders match each other, the trade is allowed and recorded as a normal execution with `buyerUserId == sellerUserId`. Deltas for the same account are combined before they are applied: cash and share totals net to zero, and both reservations for the matched quantity are released.

**Atomicity.** One submission's preflight, matching, order updates, executions, and settlement are published together or not at all.

## Order Lifecycle in Sprint 2

Statuses follow [order-model.md](order-model.md). Sprint 2 produces only `NEW`, `PARTIALLY_FILLED`, and `FILLED`. `CANCELED` needs a cancellation API (later), and `REJECTED` orders are not stored. Acceptance order is the order in which submissions pass the exchange's serialized boundary; it determines time priority.

## Resources

### Order

```json
{
  "id": "ord-2",
  "userId": "bob",
  "symbol": "AAPL",
  "side": "BUY",
  "type": "LIMIT",
  "price": 19050,
  "quantity": 25,
  "remaining": 15,
  "status": "PARTIALLY_FILLED",
  "sequence": 2,
  "createdAt": "2026-10-20T15:00:02Z",
  "updatedAt": "2026-10-20T15:00:02Z"
}
```

All fields except `sequence` are the JSON form of `orders.Order`. `sequence` is the acceptance sequence assigned by the exchange.

### Execution

```json
{
  "id": "exe-1",
  "sequence": 1,
  "executedAt": "2026-10-20T15:00:02Z",
  "symbol": "AAPL",
  "price": 19000,
  "quantity": 10,
  "buyOrderId": "ord-2",
  "sellOrderId": "ord-1",
  "buyerUserId": "bob",
  "sellerUserId": "alice"
}
```

This is the JSON form of `executions.Record` ([#32](https://github.com/co-rtex/tradegrid/issues/32)).

### Account

```json
{
  "userId": "alice",
  "displayName": "Alice (demo)",
  "cash": { "total": 10000000, "reserved": 0, "available": 10000000 },
  "positions": [
    { "symbol": "AAPL", "total": 100, "reserved": 0, "available": 100 },
    { "symbol": "MSFT", "total": 100, "reserved": 0, "available": 100 }
  ]
}
```

`positions` lists every tradable symbol, sorted by symbol, including zero holdings.

## Endpoints

Every endpoint below returns a coherent snapshot: values reflect one point between submissions, never a submission in progress.

### `POST /api/v1/orders`

Request:

```json
{ "userId": "bob", "symbol": "AAPL", "side": "BUY", "type": "LIMIT", "price": 19050, "quantity": 25 }
```

All six fields are required. Any other field, including server-owned fields such as `id`, `status`, `remaining`, `sequence`, `createdAt`, or `updatedAt`, is rejected with `UNKNOWN_FIELD`. The body must be a single JSON object with nothing after it.

Response `201 Created`, whether the order rested, partly filled, or fully filled:

```json
{
  "order": { "id": "ord-2", "status": "PARTIALLY_FILLED", "remaining": 15, "...": "full Order" },
  "executions": [ { "id": "exe-1", "price": 19000, "quantity": 10, "...": "full Execution" } ]
}
```

`executions` lists the fills this submission produced, in matching order; it is `[]` when the order only rested. The response does not include updated resting orders or accounts; read them with the GET endpoints. Clients must not retry a POST automatically.

### `GET /api/v1/orders?userId=alice&limit=50`

`userId` is required. Returns that account's accepted orders in every status, newest first (descending `sequence`).

```json
{ "orders": [ { "id": "ord-1", "userId": "alice", "status": "FILLED", "...": "full Order" } ] }
```

### `GET /api/v1/orderbook?symbol=AAPL&depth=20`

`symbol` is required. Returns resting remaining quantity aggregated by price. Bids are sorted highest price first, asks lowest first. Fully filled orders do not appear. `asOfSequence` is the acceptance sequence of the last order processed (`0` before any order).

```json
{
  "symbol": "AAPL",
  "asOfSequence": 2,
  "bids": [ { "price": 19050, "quantity": 15, "orderCount": 1 } ],
  "asks": []
}
```

### `GET /api/v1/executions?symbol=AAPL&userId=bob&limit=50`

`symbol` is required. `userId` is optional; when present, only executions where that account is buyer or seller are returned. Newest first (descending `sequence`).

```json
{ "executions": [ { "id": "exe-1", "sequence": 1, "...": "full Execution" } ] }
```

### `GET /api/v1/accounts`

Returns both demo accounts, sorted by `userId`.

```json
{ "accounts": [ { "userId": "alice", "...": "full Account" }, { "userId": "bob", "...": "full Account" } ] }
```

### `GET /api/v1/portfolio?userId=alice`

Proposed for Sprint 3 ([#69](https://github.com/co-rtex/tradegrid/issues/69)). Returns one account's cash, positions, cost basis, reference-price valuation, and realized and unrealized P&L. The response, field definitions, and errors are in [portfolio.md](portfolio.md#api-get-apiv1portfoliouseridalice). It uses no new error codes.

### `GET /api/v1/symbols`

Returns the tradable symbols, sorted by symbol.

```json
{ "symbols": [ { "symbol": "AAPL", "name": "Apple Inc." }, { "symbol": "MSFT", "name": "Microsoft Corporation" } ] }
```

## Errors

Every error response has this body. `field` names the offending request field or query parameter and is omitted when no single field is at fault.

```json
{ "error": { "code": "INVALID_PRICE", "message": "price must be between 1 and 100000000 cents", "field": "price" } }
```

`message` is for people and may change; clients branch on `code`.

| Status | `code` | When |
| --- | --- | --- |
| 400 | `MALFORMED_JSON` | Body is not one JSON object, has trailing data, or a value has the wrong JSON type (for example a string, fraction, or exponent where an integer is required, or an integer outside `int64`). |
| 400 | `UNKNOWN_FIELD` | Body contains a field not listed for the request, including server-owned fields. |
| 400 | `INVALID_QUERY` | A required query parameter is missing, or `limit`/`depth` is not an integer in its allowed range. |
| 404 | `UNKNOWN_USER` | `userId` is not a demo account (body or query). |
| 404 | `NOT_FOUND` | No such route. |
| 405 | `METHOD_NOT_ALLOWED` | Route exists but not for this method. The response includes an `Allow` header. |
| 413 | `BODY_TOO_LARGE` | Body exceeds 4096 bytes. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | A request with a body is not `application/json`. |
| 422 | `MISSING_FIELD` | A required body field is absent or an empty string. |
| 422 | `UNKNOWN_SYMBOL` | Symbol is not `AAPL` or `MSFT`, including lowercase forms. Also returned for unknown `symbol` query values. |
| 422 | `INVALID_SIDE` | Side is not `BUY` or `SELL`. |
| 422 | `UNSUPPORTED_ORDER_TYPE` | Type is not `LIMIT`. `MARKET` is a valid model value but not supported in Sprint 2. |
| 422 | `INVALID_PRICE` | Price is outside `1`..`100000000`. |
| 422 | `INVALID_QUANTITY` | Quantity is outside `1`..`1000000`. |
| 422 | `INSUFFICIENT_CASH` | A BUY needs more available cash than the account has. |
| 422 | `INSUFFICIENT_SHARES` | A SELL needs more available shares than the account has. |
| 422 | `LIMIT_EXCEEDED` | The submission would push an aggregate past its bound. |
| 500 | `INTERNAL` | Unexpected failure. Nothing was published. |

When several rules fail, the first in this order wins: decoding (400), then `userId` (404), then field validation in table order, then risk.

## Go Interfaces

These are the internal seams between Sprint 2 issues. Names may be adjusted in review, but the responsibilities should not move.

```go
// package exchange (#33, #35): the only owner of book, orders, executions, and accounts.
type Service interface {
	Submit(req SubmitRequest) (SubmitResult, error) // serialized; atomic
	Orders(userID string, limit int) ([]OrderView, error)
	OrderBook(symbol string, depth int) (BookSnapshot, error)
	Executions(symbol, userID string, limit int) ([]executions.Record, error)
	Accounts() []AccountSnapshot
}

// SubmitRequest carries only client-owned fields (#36 decodes into it).
type SubmitRequest struct {
	UserID, Symbol, Side, Type string
	Price, Quantity            int64
}

// package risk (#34): pure calculations, no state of its own.
// Preflight checks an account can afford an order and returns the reservation.
// Settle returns new account values for a batch of executions, netting
// same-account deltas. Neither mutates its inputs.
```

Errors returned by the service wrap a typed error carrying the `code` above, so the HTTP layer maps it without matching message text. Snapshot methods return copies.

## Database Mapping

The runtime exchange does not use the database in Sprint 2. For [#12](https://github.com/co-rtex/tradegrid/issues/12)/[#39](https://github.com/co-rtex/tradegrid/issues/39), the schema should be able to store exactly the resources above: integer cents and shares, both execution counterparties (order and user), original and remaining quantity with status, and the order and execution `sequence` values used for ordering. Column names and table layout are #12's decision, documented in [PostgreSQL Schema Design](database-schema.md).
